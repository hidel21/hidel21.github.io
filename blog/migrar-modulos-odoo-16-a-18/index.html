Migrar módulos de Odoo 16 a 18: los cambios que rompen tu código

Los datos se migran con herramientas; el código propio, a mano. Estos son los cambios de Odoo 17 y 18 que más módulos personalizados rompen, con el antes y el después de cada uno.

Por Hidelberg Martínez · 4 de noviembre de 2026 · 8 min de lectura

En resumen: al pasar un módulo de Odoo 16 a 18 hay que (1) reemplazar attrs y states por expresiones en invisible, readonly y required; (2) cambiar name_get por _compute_display_name; (3) renombrar las vistas tree a list, incluidos los xpath; (4) usar aggregator en lugar de group_operator; (5) reemplazar el bloque del chatter por <chatter/>; y (6) escribir scripts de migración para los campos renombrados.

1. Vistas: adiós a attrs y states (Odoo 17)

Es el cambio que más vistas rompe. Desde Odoo 17, los dominios dentro de attrs y el atributo states ya no se aceptan: la visibilidad y la obligatoriedad se escriben como expresiones de Python directamente en invisible, readonly y required.

Odoo 16 
<field name="partner_id"
       attrs="{'invisible': [('state', '!=', 'draft')],
               'required': [('move_type', '=', 'out_invoice')]}"/>
<button name="action_confirm" type="object" states="draft"/>
Odoo 17 / 18 
<field name="partner_id"
       invisible="state != 'draft'"
       required="move_type == 'out_invoice'"/>
<button name="action_confirm" type="object" invisible="state != 'draft'"/>

En listas, para ocultar la columna completa usa column_invisible. Un truco para la migración: busca en tu módulo grep -rn "attrs=\|states=" views/ y convierte cada dominio a su expresión equivalente, cuidando que | y & se traduzcan a or y and.

2. name_get pasa a _compute_display_name (Odoo 17)

Si tu modelo personalizaba cómo se muestra un registro en los campos relacionales, name_get dejó de ser el mecanismo. Ahora se calcula el campo display_name.

Odoo 16 
def name_get(self):
    return [(rec.id, f"[{rec.code}] {rec.name}") for rec in self]
Odoo 17 / 18 
@api.depends('code', 'name')
def _compute_display_name(self):
    for rec in self:
        rec.display_name = f"[{rec.code}] {rec.name}"

Si además querías buscar por código desde un campo Many2one, en lugar de sobrescribir _name_search basta con declarar _rec_names_search = ['code', 'name'] en el modelo.

3. Las vistas tree ahora son list (Odoo 18)

Odoo 18 renombró el tipo de vista. Hay que actualizar la etiqueta raíz, los view_mode de las acciones y, muy importante, los xpath de las vistas heredadas.

Odoo 16 / 17 
<tree string="Comisiones">...</tree>
<field name="view_mode">tree,form</field>
<xpath expr="//tree/field[@name='amount']" position="after">
Odoo 18 
<list string="Comisiones">...</list>
<field name="view_mode">list,form</field>
<xpath expr="//list/field[@name='amount']" position="after">

Los xpath heredados son los que más fallan en silencio: la instalación se detiene con un error de «elemento no encontrado». Revísalos todos antes de actualizar.

4. group_operator pasa a aggregator (Odoo 18)

El parámetro que define cómo se agrupa un campo numérico en listas y tablas dinámicas cambió de nombre. El nombre viejo genera advertencias de obsolescencia.

Odoo 16 / 17 
amount = fields.Monetary(group_operator="sum")
Odoo 18 
amount = fields.Monetary(aggregator="sum")

5. El chatter se simplifica (Odoo 18)

En los formularios, el bloque del chatter con sus tres campos se reemplaza por una sola etiqueta.

Odoo 16 / 17 
<div class="oe_chatter">
    <field name="message_follower_ids"/>
    <field name="activity_ids"/>
    <field name="message_ids"/>
</div>
Odoo 18 
<chatter/>

6. JavaScript heredado

Si tu módulo tiene JavaScript escrito con odoo.define o widgets del framework anterior, no basta con renombrar: hay que reescribirlo como módulos ES y componentes Owl. Es la parte más costosa de muchas migraciones, así que conviene estimarla por separado.

7. Scripts de migración de datos

Cuando cambias el nombre de un campo o la estructura de un modelo propio, los datos existentes no se mueven solos. Odoo ejecuta los scripts que encuentre en una carpeta con la nueva versión del módulo, la misma que declaras en el __manifest__.py:

Estructura 
mi_modulo/
├── __manifest__.py          # "version": "18.0.1.0.0"
└── migrations/
    └── 18.0.1.0.0/
        ├── pre-migrate.py   # antes de actualizar el esquema
        └── post-migrate.py  # después de actualizar el esquema
pre-migrate.py 
def migrate(cr, version):
    # Conserva los datos al renombrar un campo: commission_amount -> amount
    cr.execute("""
        SELECT 1 FROM information_schema.columns
        WHERE table_name = 'commission_line' AND column_name = 'commission_amount'
    """)
    if cr.fetchone():
        cr.execute("ALTER TABLE commission_line RENAME COLUMN commission_amount TO amount")

Sin este paso, Odoo crea la columna nueva vacía y la vieja queda huérfana: los datos «desaparecen» aunque sigan en la base.

Lista de verificación antes de salir a producción

  • Todos los módulos propios instalan y actualizan sin errores sobre una copia de la base de producción.
  • Ninguna vista usa attrs, states, tree ni group_operator.
  • Los xpath heredados apuntan a elementos que existen en la versión destino.
  • Los campos renombrados tienen su script de migración y se verificaron con datos reales.
  • Los usuarios clave compararon cierres contables, nómina e informes contra la versión anterior.
  • Hay respaldo, ventana de corte acordada y plan de reversión.

Preguntas frecuentes

¿Puedo migrar directamente de Odoo 16 a Odoo 18?

Los datos sí, con el servicio de actualización de Odoo (Enterprise); con OpenUpgrade (Community) se avanza versión por versión. El código propio debe incorporar los cambios de la 17 y de la 18 a la vez, que son justamente los de esta guía.

¿Qué es lo que más se rompe al migrar un módulo de Odoo?

Las vistas: attrs y states en Odoo 17, y las vistas tree y sus xpath heredados en Odoo 18. Después, el JavaScript heredado.

¿Cómo evito perder datos al renombrar un campo?

Con un script pre-migrate.py que renombre la columna antes de que Odoo actualice el esquema, dentro de la carpeta migrations/ con la versión nueva del módulo.

¿Tu migración tiene más de un par de módulos?

Lideré la migración de Nómina, Contabilidad y Presupuesto de Odoo 14 a 18 sin detener la operación. Cuéntame qué versión tienes y te propongo un plan.
